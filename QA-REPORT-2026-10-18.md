## Findings and required follow-up

### QA-F1 — Expected SSE disconnects are reported as dashboard errors (P2)

During the 120-second soak, the harness created 7,227 connect/read/disconnect cycles, including five clients held stalled for the run. The test passed its cleanup checks: zero connected clients remained, zero SSE client errors were recorded, and the dashboard shut down cleanly. However, the dashboard's error callback counted 1,786 errors; the first sample was `Error: write EPIPE`.

In [src/dashboard/server.ts](src/dashboard/server.ts), `isDisconnect()` recognizes `ECONNRESET` and the message `aborted`, but not `EPIPE` (lines 86–88). SSE response/socket errors go through that classifier and other errors are reported (around the `handleSse` error handler). This makes normal peers closing while the server writes look like server faults and can produce noisy warnings during client churn.

**Recommended fix:** classify `EPIPE` as an ordinary disconnect and keep cleanup idempotent. Add a regression test that closes an SSE client while events are being written and asserts it does not invoke `onError`; retain a case proving genuine server errors are still reported.

Evidence: [soak JSON results](/private/tmp/phargus-soak-qa.json).

**Remediation — fixed.** `isDisconnect()` in `src/dashboard/server.ts` now treats `code === 'EPIPE'` like `ECONNRESET` and `aborted`. That one classifier covers the SSE response and socket handlers, the static-asset handler, the session body and `clientError`. Anything else is still reported. Cleanup is unchanged and still guarded by its `done` flag, so a second error or close after cleanup does nothing.

New tests in `src/dashboard/dashboard-sse-disconnect.integration.test.ts` (7 cases):

- 30 real clients reset (`resetAndDestroy`) while windows are being written, then more writes after every peer is gone: `onError` is never called and every client is cleaned up. This case **failed before the fix**, so it reproduces the bug with real sockets.
- `EPIPE`, `ECONNRESET` and `aborted` emitted on the SSE response: not reported, client removed, and a repeated error after cleanup does not throw or change the count. The `EPIPE` case failed before the fix.
- `EPIPE` on the SSE socket: not reported. It failed before the fix (it was reported twice).
- A genuine error (`ENOSPC`) on the SSE response is reported exactly once through `onError`, and the client is still cleaned up.
- With no `onError`, a genuine error becomes the `dashboard server error: …` process warning and an `EPIPE` produces none. The `EPIPE` half failed before the fix.

The same file passed 5 consecutive runs after the fix.

Soak rerun after the fix ([JSON](/private/tmp/phargus-soak-2026-10-18-after-fix.json), [table](/private/tmp/phargus-soak-2026-10-18-after-fix.md)): all 12 checks passed, **0 dashboard errors** over 7,273 connect/read/disconnect cycles with 5 stalled clients, 0 SSE clients left connected, 0 SSE client errors. App heap after GC +1.7% and collector +5.6% (limit +10%). 2,168,550 requests (17,820 rps) with 0 errors.

### QA-F2 — Overhead measurement does not establish the low-overhead requirement (P2 follow-up)

The full benchmark ran all 60 workload/variant/round cells on Node 22.18.0. It reported high throughput variation across rounds: CV ranged from 13.4% to 48.5%. In the reported medians, the `full` variant used about 23% more CPU per request and 27% more RSS for the trivial workload, and about 31% more CPU/request and 45% more RSS for the promise workload. The `tracing` variant showed about 37% more CPU/request and 50% more RSS for the promise workload. Stream results also varied heavily, including a similar throughput drop for the agent-off baseline, so those deltas are not dependable.

The harness completed successfully, but there is no pass/fail performance budget, and the high CV prevents a confident conclusion from this run. The Node 22 tracing cost is documented in README, but the measured CPU/RSS deltas are still worth resolving against the stated negligible-overhead goal.

**Recommended follow-up:** rerun on an idle, stable host (or repeat until CV is within the project's expected range), then define CPU/request and memory overhead budgets for the supported workloads. Treat this run as a warning signal, not a confirmed regression.

Evidence: [overhead benchmark JSON](/private/tmp/phargus-overhead-qa.json).

**Remediation — confirmed, partly reduced, still unresolved.**

_Host._ The same Apple M2, Node 22.18.0, full default run (`node bench/overhead.mjs`: 60 cells, 3 rounds, 5 s measured, 32 connections), JSON saved outside the repository. The host never got below about 20% CPU busy: WindowServer, a browser and the Claude app ran throughout, and macOS's load average stayed between 3 and 7. A wait of about 8 minutes for at least 90% idle CPU never succeeded, so each run's CV is the reliability test (bench/README: typical noise 3–8% CV; treat a delta under about twice the CV as noise).

The original QA medians (`full` +22.9% CPU / +26.6% RSS trivial and +31.4% / +45.3% promise; `tracing` promise +37.4% / +50.1%) reproduce on stable data, the CPU deltas somewhat higher. The cost is all tracing: `samplers` and `idle` match `none` within about 1%. Under tracing, GC runs about half as often but total pause time is 2.5× (trivial 40.7 → 101.1 ms).

_Investigation._ CPU profiles (`--cpu-prof`) of the `trivial` target:

- `crypto.randomFillSync`, behind `randomBytes()` in `newTraceId()` and `newSpanId()` (two native calls and two Buffers per request), was **about 16% of busy CPU** in the traced server.
- The rest of the tracing cost is Node 22's `async_hooks` machinery behind `AsyncLocalStorage` (`emitInit*`, `_propagate`, about 7%) and the tracer's own `onStart`/`onFinish` plus `diagnostics_channel` (about 5%).

_Change._ `src/agent/trace-id.ts` cuts ids from a 4 KiB `randomFillSync` pool: same CSPRNG source, the same lowercase-hex and never-all-zero contract, and no byte reused. New `src/agent/trace-id.pool.test.ts` has 4 cases (all failed before the change): format, uniqueness and refills; batched draws; zero-fill skipping; no byte reuse.

_After the change._ The full run (run 2) and its one allowed repeat (run 3) were both noisier than 3–8%, so **the after-change benchmark result is inconclusive under the rule set for this follow-up.** The comparison below uses only cells whose own rps CV was at most 8% in both runs. It is supporting evidence, not a verdict:

| promise                        | +48.3% → +28.6%           | −10.0% → +1.0%     | +48.7% → +46.5%    |

Exploratory single-round profiling runs, before and after, agreed: trivial `tracing` CPU went from +33.2% to +15.8%, GC pause from 110 to 52 ms, and the `randomFillSync` frames are gone from the after profile.

_RSS, root-caused but not fixed._ Under tracing, `heapUsed` grows only about 3–4 MiB. What grows is V8's young generation, from 8 to 32 MiB (`new_space`). The trigger is the tracer's 1024-span drop-oldest buffer: at about 50k requests/s each span lives about 20 ms, survives scavenges, and drives V8 to its maximum semi-space size. With `spanBufferSize: 16`, RSS falls to what bare `AsyncLocalStorage` costs (72 vs 71–72 MiB). Changing the default size or drop policy would retain fewer spans at ordinary request rates, so it was left as an open product decision, not tuned here.

**Remaining limitation at that point:** on Node 22 tracing still cost roughly +16% (trivial) to +29% (promise) CPU per request (indicative), and RSS stayed high. Both were followed up below.

**Follow-up (pharn-dev/phargus#93) — memory fixed, cost measured on clean hosts.**

_Clean measurements._ The full default benchmark ran on GitHub-hosted runners through the nightly workflow's manual trigger, which is a quieter host than the laptop:

- [39110592410](https://github.com/pharn-dev/phargus/actions/runs/39110592410): scheduled nightly, before #92.
- [39155616030](https://github.com/pharn-dev/phargus/actions/runs/39155616030): `main` after #92.
- [39159577079](https://github.com/pharn-dev/phargus/actions/runs/39159577079): the #93 branch.

Every run met the 3–8% CV bar in at least 19 of 20 cells. Each landed on a different runner CPU (EPYC 9V45, 7763 and 9V74), so only within-run deltas against `none` are compared. The 7763 run was load-generator-bound (server ELU 0.54–0.59), which understates per-request cost.

_The earlier memory diagnosis was wrong and is corrected here._ 60–120 s runs with heap-after-GC and `--trace-gc-nvp` showed the following:

- After a minute or two of load V8 grows its young generation to the same maximum with or without the agent. Much of the benchmark's 5 s RSS delta is that growth happening sooner under tracing, not retention.
- The real cost was **old-generation churn**. Each buffered span (an object plus four strings) lived about 20 ms in the 1024-slot ring against a scavenge every few ms, so it was promoted and died there. Promoted per 20 s on promise: 4.1 MiB with no agent, **12.7 MiB** with tracing, and 4.7 MiB with a 16-span buffer. Promise RSS after 60 s averaged 79 MiB without the agent and 104 MiB with tracing.
- The first fix attempt (fields in typed arrays, path still a string) did not help: 12.7 MiB was still promoted. Not storing the path brought promotion to 4.8 MiB, which identified the path string as the last survivor.

_Fix._ The span buffer stores ids, path (Latin-1 bytes, 256 per slot, with a string fallback) and numbers in preallocated slots, and builds the name at drain. The tracer writes span ids straight from the CSPRNG pool. Buffered, dropped and exported data are unchanged. New tests: 5 buffer cases (the 4 written first failed on `main`, including a `WeakRef` + `gc` retention check) and 1 `writeSpanId` case.

_Result._

- Promotion per 20 s: promise 4.5 MiB against 4.1 with no agent; trivial 3.0 against 3.1.
- Promise RSS after 60 s (×3): 68–86 MiB, avg 76, against avg 76 without the agent.
- On the #93 runner run, `tracing` against `none`: RSS +2.4% (trivial), +1.8% (cpu), −3.3% (stream). Promise reads +21.4% because of the documented 5 s young-generation timing effect. GC ms on trivial is 36.4 against 36.5 (before #92: 159 against 37).
- CPU per request +9.8% to +12.9%; saturated throughput −9.7% (`cpu`) and −9.9% (`stream`). Before #92 the same deltas were +20.6% to +40.1% CPU per request and −16% throughput.
- A per-span microbenchmark shows `record()` at 133 ns/span against `main`'s 120. That is under 0.1% of a request.

_Still true, and documented in `docs/LIMITS.md` §1:_ on Node 22 tracing costs about 10–13% CPU per request and about 10% throughput when CPU-bound, mostly `AsyncLocalStorage` on `async_hooks` (mitigation: `--experimental-async-context-frame`). No overhead budget is defined, so whether this counts as "negligible" is a maintainer decision.
