# Phargus — independent engineering review (2026-10-12)

Reviewed: `main` at `aad3a14` (`ci(release): publish on merge of a version bump (#63)`), package `@pharn-dev/phargus@0.1.0`.
Method: read all 9.7k lines of non-test source, the scripts, CI and docs; ran every gate on Node 24.13.1 and the test suite on the Node 22.18.0 floor; ran seven targeted probes against `dist/` and the `bench/overhead.mjs` harness. Every finding cites `file:line` against this commit.

## Context

- **Repo purpose:** in-process runtime diagnostics for Node.js (event loop, memory, GC, stream backpressure, HTTP request traces) with an optional collector, live dashboard, analyzer, rule sandbox and OTLP export.
- **Target users:** Node.js developers and SREs who want a quick live look at one process without an APM account.
- **Runtime / distribution:** npm library with six subpath exports (ESM + CJS), Node ≥ 22.18. No CLI.
- **Maturity goal:** production-ready OSS, first release already on npm.

---

## 1. Verdict: FIX FIRST

The core engineering is unusually careful for a 0.1: every buffer is bounded and counted, prototype patches are reversible and double-load safe, the release pipeline is split so no job that installs dependencies can mint a publish token, and 225 real integration-heavy tests pass on both the Node floor and Node 24. The product, however, does not yet deliver its headline. "One line in your process" gives you 2 KB/s of JSON on stdout; the dashboard needs a second program you write yourself, and the one the README gives you dies on the first log line your app prints (verified). Three further verified data-loss defects sit on the paths users will hit first: a fresh dashboard client loses its initial alerts, the OTLP trace exporter dropped 87% of a 500-span burst, and aborted or timed-out requests never produce a span. None of these is a security hole and all are fixable in days, which is why this is FIX FIRST rather than RETHINK. Ship after the first five PRs in §7.

## 2. How it actually works

1. **Agent** (`src/agent/auto.ts:5` → `auto-start.ts:145-159`): importing the subpath starts the agent once per process (a `Symbol.for` flag on `globalThis`). Before config is even loaded it wraps `http.Server.prototype.emit` and subscribes to the `http.server.request.start/response.finish` diagnostics channels (`http-tracing.ts:258-271`) so every incoming request runs inside an `AsyncLocalStorage` context with a trace id. It wraps `write` on `Writable`, `Duplex` and `OutgoingMessage` prototypes to detect `write() === false` stalls and time them to `drain` (`backpressure-probe.ts:297-306`). Every `intervalMs` a `setInterval` (unref'd) reads the event-loop histogram, `process.memoryUsage()`, `v8.getHeapSpaceStatistics()`, a GC `PerformanceObserver` and the backpressure window (`sampler-controller.ts:65-80`).
2. **Transport:** two drop-oldest ring queues (samples, spans; `queueBound` each) feed one `stream/promises` `pipeline()` into `process.stdout` or an append-only file (`ndjson-exporter.ts:58-75`, `agent-output.ts:13-19`). Sample lines carry cumulative `dropped` counters. Config = defaults ← `phargus.config.{json,js}` in cwd ← `PHARGUS_*` env (`config.ts:23-31`).
3. **Collector** (`collector.ts:118-156`): the _caller_ turns NDJSON into objects; `consume()` runs a Transform pipeline: span router → fixed-window aggregator (integer math) → ring buffer + subscribers → optional append-only persistence (awaited in-line) → edge-triggered alert evaluator → sink dispatcher (stdout / file / webhook).
4. **Dashboard** (`server.ts:252-303`): `node:http`, three in-memory assets, `/events` SSE with a per-client bounded FIFO; `Host`/`Origin` allowlist; `?token=` on `/` exchanged for an HMAC cookie; token mandatory off loopback.
5. **Analyzer:** a worker pool with V8 `resourceLimits`; a streaming JSON tokenizer for heap snapshots; a source-map symbolizer confined by `realpath` to `roots`.
6. **Plugin runner:** one forked child, a fresh `isolated-vm` isolate per rule run, results size-capped inside the isolate and re-validated on the host.
7. **OTel:** per-window metrics POST and per-span trace POST through a sequential drop-newest queue.
8. **Release:** `gate → build → publish → release` with OIDC Trusted Publishing, SHA-pinned actions, CodeQL, gitleaks, tarball and install-smoke checks.

**Mismatches between docs and code**

- README (`README.md:10`, `:99-116`) sells "one line" and a dashboard; the dashboard requires a user-written collector process, and the README's collector crashes on any non-JSON stdout line (F1).
- `ARCHITECTURE.md` diagram shows the plugin runner subscribed to collector windows; no code connects them, and rule findings reach no sink, dashboard or export (F12).
- `CLAUDE.md:149` and `ARCHITECTURE.md:106` require "negligible" overhead; measured cost is ~4 µs CPU per request (+25–29%) and +50–110 MiB RSS, and no number is published anywhere (F9).
- README says an incoming W3C `traceparent` is "continued"; the parent span id is discarded, so exported spans are roots (F6).
- `SECURITY.md` says binding off loopback "requires a token"; a one-character token is accepted (F7).

## 3. Top 5 risks (impact × likelihood)

1. **Stdout as the transport, with brittle consumers.** Any `console.log` kills the README collector; any JSON log line (pino, winston) kills the collector library itself (both verified, F1). Likelihood: near-certain for every real app. This is the first thing a new user hits.
2. **OTLP trace export is unusable above a few spans per second** (F2). Users who adopt "OTel integration" get silently sampled, newest-dropped data and will not notice until they compare counts.
3. **The dashboard hides what matters at 2 am:** alerts are dropped from the initial replay (F3) and aborted/timed-out requests never appear (F5). Both erode trust in the data precisely when it is needed.
4. **Production footguns in the recommended alternatives:** file output grows without bound (F8), spans above ~1000 per interval are dropped with no sampling control (F13), and a short token is accepted on `0.0.0.0` (F7).
5. **Repository hygiene will generate the first wave of issues:** 7.3 MB / 765 files of unrelated tooling, a second threat model and limits doc at the root, committed agent hooks that block contributors' writes, and a 33-symbol agent API that will need breaking changes (F14, F18).

## 5. What's genuinely good

- **Release pipeline** (`.github/workflows/publish.yml`): the job that can mint the OIDC publish token checks out nothing and installs nothing; `scripts/check-publish-workflow.mjs` pins the job graph and permissions and _executes_ the gate script against a stub `git` under `npm test`. This is better than most 1.x projects.
- **Bounded-everything discipline:** agent lanes, span buffer, SSE FIFO, OTLP queue, worker queue, rule result size, response-body discard cap, hotspot sites per window; each with a counter and a test (`collector-bounds`, `otlp-bounds`, `sse-client-retention`, `export-loss`).
- **Heap-snapshot worker** (`src/analyzer/workers/heap-snapshot.worker.ts:1-11, 109-310`): a streaming JSON tokenizer written specifically because one native `JSON.parse` past a worker's heap limit aborts the whole process. The reasoning is in the header comment and matches V8's behaviour.
- **Prototype patching done right** (`src/agent/backpressure-probe.ts:68-87`, `src/agent/http-tracing.ts:94-109`): per-install records, identity-guarded restore that never clobbers a later wrapper, a `globalThis` registry so an ESM and a CJS copy share one install, arity-preserving wrappers, observers that cannot throw into the host.
- **Tests that test the product:** 105 files, 67 integration, zero `vi.mock`; they compile the agent with the real `tsc`, fork real processes, run under `--permission`, and pass on both 22.18.0 and 24.13.1 (verified locally, 225/225 each).

Unless a test shows a real library doing that, the active/inactive pass-through already makes it harmless; the peeling is complexity without a demonstrated need.
